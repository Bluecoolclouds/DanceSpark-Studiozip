## Граница текущего этапа

Встроенный платёжный сценарий агента не предоставляет подключения RuStore Pay SDK. У него нет готового подключённого провайдера RuStore. Это ограничение текущего сценария, **не утверждение**, что RuStore невозможно реализовать в React Native или развернуть серверную часть.

Официальная инструкция RuStore требует Android native-модуль, Gradle-зависимость, регистрацию пакета, metadata приложения и обработку платёжных deeplink. Это не JS-only библиотека и не работает в стандартном Expo Go. Нативная интеграция в этой подготовке не выполнялась; подставной SDK, имитация успешной оплаты или открытие платного доступа не добавлялись.

## Что нужно реализовать и проверить до включения

1. Подключить официальный Android Pay SDK в процессе сборки, поддерживающем его нативный модуль. Сохранить текущие package, сертификат, Better Auth и работу Expo web. Отдельно проверить совместимость с используемой React Native/New Architecture.
2. Настроить `console_app_id_value`, возврат из банковского приложения и изолированную платёжную deeplink-схему без конфликта с `danceflow` auth-ссылками.
3. Получать товары и реальные цены из SDK; сопоставлять только разрешённые Product ID. Недоступные/неизвестные товары не подменять другими.
4. На сервере создавать привязку операции к проверенному аккаунту Danceflow; валидировать покупку через RuStore API. Не доверять клиентскому «успеху» и не выдавать доступ по одному Product ID.
5. Обеспечить уникальность покупки и атомарную выдачу периода, обработку продлений/отмен/возвратов и повторных уведомлений. Не переносить одну магазинную подписку между разными аккаунтами автоматически.
6. Восстанавливать оплаченный доступ на другом устройстве через тот же аккаунт Danceflow. Не полагаться только на список покупок текущего устройства.
7. Показывать отмену и реальную дату окончания оплаченного доступа. Удаление аккаунта согласовать с прекращением будущих продлений, не скрывать продолжающиеся списания.
8. Настроить публичный HTTPS API для уведомлений и сверки, production-БД, секреты API только на сервере. Запрашивать секреты через защищённое хранилище, не в чате.
9. Проверить подписанный Android-релиз и тестовый платёжный контур. Только после проверки отдельно разрешать реальные покупки и менять `PAYMENTS_CONNECTED`.

## Авторизация и условия RuStore

Better Auth остаётся авторизацией Danceflow. По официальному руководству RuStore, покупка подписки требует авторизации VK ID в платёжном интерфейсе; это не причина менять вход приложения на VK.

Собственный SMTP для платежного SDK не нужен. Но отсутствие SMTP не устраняет требования к поддержке, документам и обработке проблем с аккаунтом.

По руководству RuStore, для приёма платежей приложение должно быть загружено в консоль и пройти модерацию; публиковать его при этом необязательно. Подключённая монетизация сама по себе не доказывает прохождение этих условий.

Для веба прежний план ЮKassa отдельно сохранён, но тоже не реализован. Не открывать магазинный native SDK из браузера и не показывать оплату на iOS в рамках этого этапа.
