# Better Auth: вход и эксплуатация

Danceflow использует Better Auth внутри существующего Express API и PostgreSQL.
Clerk и Logto не участвуют во входе; старые аккаунты у этих поставщиков и их
секреты автоматически не удаляются. Старые сессии не принимаются, нужен новый вход.
Самостоятельное размещение библиотеки не означает размещение данных в РФ:
географию серверов, базы и договоры необходимо проверить отдельно.

## Конфигурация и запуск

- `pnpm install --frozen-lockfile`, затем существующий `pnpm --filter @workspace/db run push`
  для development. Добавляются отдельные таблицы авторизации; `df_accounts` и её ID сохраняются.
  Для базы с данными предварительно просмотреть миграцию; не очищать базу и не применять
  изменения к production без отдельного согласования и резервной копии.
- Секрет подписи: `BETTER_AUTH_SECRET`, иначе уже настроенный `SESSION_SECRET`,
  не менее 32 символов. Не помещать в Git, команды терминала или клиентские переменные.
- Доверенные HTTPS origins берутся из текущих доменов среды и дополнительного
  `DANCEFLOW_WEB_ORIGINS` (список через запятую). Удаляйте устаревшие origins при переносе;
  не используйте wildcard для веб-доменов. Сервер не доверяет произвольному Host.
- Web и админка обращаются к `/api/auth` на своём origin. Сессия восстанавливается
  через Secure/HttpOnly/SameSite=Lax cookies; API получает ограниченный текущей
  учётной записью токен в памяти, не в localStorage.
- Native использует официальный Expo plugin, SecureStore и `danceflow` scheme.
  В релизе обязателен `EXPO_PUBLIC_API_ORIGIN` с реальным HTTPS API;
  development использует текущий домен среды. Парольный вход не требует OAuth callback.
- Сессии имеют срок 7 дней, обновление раз в сутки; cookie-cache отключён.
  Состояние роли/блокировки сверяется сервером в каждом защищённом API-запросе.
  Проверка сессии в клиенте повторяется при фокусе окна и каждые 30 секунд.
- Ограничения API Better Auth хранятся в БД, действуют и в development:
  вход 5 попыток/минуту, регистрация 5/час по источнику запроса.

## Пока нет SMTP

Работают регистрация и вход по email/паролю (10–128 символов), выход и восстановление
существующей сессии. Email остаётся **неподтверждённым**.
Письма подтверждения и восстановления пароля не отправляются; интерфейс не сообщает
об успешной отправке. При потере пароля требуется отдельная безопасная процедура
оператора, пока не подключён SMTP. Указание чужого адреса не подтверждает владение им.

## Назначение владельца

1. Владелец регистрирует новый аккаунт обычным способом.
2. Оператор с доверенным доступом к терминалу устанавливает принадлежность аккаунта
   независимо от введённого email и находит его **внутренний ID**.
3. Запускает `pnpm --filter @workspace/api-server auth:operator grant-owner <internal-account-id> --ownership-verified`.

Это не публичная кнопка или HTTP-маршрут. Процедура меняет только явно указанный
действующий аккаунт, не принимает email как доказательство и пишет событие аудита.
Здесь нет автоматического назначения первой зарегистрированной учётной записи.

## Перенос старого аккаунта

Пароли Clerk/Logto не импортируются. Обычная регистрация с email старого аккаунта
отклоняется, чтобы не присвоить его историю и роль.

После независимого подтверждения владения оператор запускает в интерактивном
доверенном терминале:

`pnpm --filter @workspace/api-server auth:operator migrate <existing-internal-account-id> --ownership-verified`

Инструмент запрашивает новый пароль скрытым вводом; его нельзя передавать в argv,
чат или лог. Он создаёт отдельную учётную запись Better Auth и явную связь с
существующим внутренним ID. История, тариф, баланс и роли не изменяются; адрес не
помечается подтверждённым. Если адрес/привязка уже заняты, операция отклоняется,
без автоматического объединения. Старые учётные записи у провайдеров не удаляются.

До переключения опубликованного сервиса с действующими пользователями:
сделать резервную копию, проверить принадлежность и перенести владельца, проверить
новый вход и права, затем согласовать cutover. Эта задача не публикует изменения
и не меняет production-базу. Старую рабочую опубликованную версию не отключать до
проверки доступа в новой.

## Удаление

Сохраняется подтверждение удаления и защита незавершённых генераций/последнего
администратора. Очистка удаляет локальные Better Auth credentials и все сессии,
затем личные записи и привязки. Старые внешние аккаунты Clerk/Logto при этом не
удаляются: ими оператор управляет отдельно. Общий каталог не затрагивается.

## Проверки

`pnpm run typecheck`

`pnpm --filter @workspace/api-server test`

Тесты используют одноразовый PostgreSQL и синтетические данные, не application DB.
Покрыты реальное хеширование/вход/отзыв сессии, неподтверждённая почта, запрет
захвата старого email, стабильные ID и права, блокировки и удаление. Браузерная
проверка не заменяет проверку Android на физическом устройстве.

Документация: [Express](https://www.better-auth.com/docs/integrations/express),
[Expo](https://www.better-auth.com/docs/integrations/expo),
[Database](https://www.better-auth.com/docs/concepts/database),
[Bearer](https://www.better-auth.com/docs/plugins/bearer).
